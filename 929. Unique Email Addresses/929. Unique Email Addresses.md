# 問題

- 有効なメールアドレスのリストemailsを受け取り、実質的に異なるメールアドレスの数を返す問題。
- 有効なメールアドレスemails[i]は {local_name}@{domain_name} というフォーマットで。
- local_name内に"."が含まれる場合、"."を除いたアドレスに。
- local_name内に"+"が含まれる場合、最初の"+"より後ろは無視。
- 入力の制約
    - emails[i]はただ1つの@を持ち、そのほか英語、"+"、"."からなる。
    - local_nameもdomain_nameも空にはならない。
    - local_nameは"+"で始まらない。
    - domain_nameは常に.com接尾辞で終わり、@と.comの間に最低でも1文字を持つ。

# Step 1

- 問題文通り、 `local` と `domain` で別々に文字を置き換え
- `local` ： `+` 以下は無視、 `.` は 空白に置き換え
- `domain` ：特に何もしない

```python
class Solution:
    def numUniqueEmails(self, emails: List[str]) -> int:
        unique_emails = set()

        for email in emails:
            local, domain = email.split('@')

            if '+' in local:
                local = local.split('+')[0]

            local = local.replace('.', '')
            
            unique_emails.add(local + '@' + domain)

        return len(unique_emails)
```

- 文字列はイミュータブルなことに注意
    - メソッドを使って書き換える
- `if "+" in local:` は `split` メソッドのためのイディオム
- https://docs.python.org/ja/3.5/library/stdtypes.html?highlight=split#str.split

1. RFC5322の複雑性
- https://tex2e.github.io/rfc-translater/html/rfc5322.html
    - **ローカルパート（`@`の前）の自由度:**
        - 英数字だけでなく、`! # $ % & ' * + - / = ? ^ _`{ | } ~` といった多くの記号が使用可能。
        - ローカルパート全体を `"`（ダブルクォート）で囲むと、スペースや `()` 、カンマ `,` などの特殊文字も許容（例: `"John Doe"@example.com`）。
    - **ドメインパート（`@`の後）の複雑さ:**
        - IPアドレスを直接指定することも可能（例: `user@[192.168.1.1]`）。
        - 国際化ドメイン名（IDN）により、非ASCII文字（日本語ドメインなど）もPunycodeに変換される。
- https://docs.python.org/ja/3.13/library/email.utils.html モジュールの使用が妥当？

1. 正規表現とセキュリティ意識
- 正規表現：
    - 文字列のパターンを表現するための特殊な記法
- ReDoS（Regular Expression Denial of Service）の危険性：
    - 複雑な正規表現（特にネストされた量指定子  や `+` を含むもの）は、特定の文字列を評価する際に、計算量が指数関数的に増大するカタストロフィック・バックトラッキングを引き起こすことがある。
    - サーバーのCPUリソースを食いつぶし、サービス停止（DoS）に追い込むことが可能。
- 単純な正規表現（例: `[^@]+@[^@]+`）で大枠を捉え、残りは別の方法で検証するのがよさそう

1. 構文チェック（Validation）と 実在確認（Verification）の切り分け
- **Validation（構文チェック）の限界:**
    - 文字列がメールアドレスの形式を満たしているかを確認する。しかし、`test@example.com` のように、形式は正しくても実在しないアドレスは無数にある。
    - ユーザーが単にスペルミスをした場合（`gmail.con` など）も、Validationでは正しい形式として通過してしまうことがある。
- **Verification（実在確認）の必要性:**
    - メールアドレスが実際に存在し、かつそのユーザー本人のものであるかを証明する唯一の方法は、実際にメールを送り、アクション（リンクのクリックやワンタイムパスワードの入力）を要求すること。
- Validationは完璧である必要はない。なぜなら、最終的な真の確認はVerificationで行うから。
- Validationはあくまで明らかに間違っている入力を早期に弾き、無駄なメール送信処理やエラーを減らすためのフィルターという位置付け。
- 例外もあり
    - **ケースA: 厳密なValidationと制御が必要な場合（B2B SaaSなど）**
        - **要件:** フリーアドレス（gmail.comなど）を禁止し、企業のドメインのみに制限したい。
        - **アプローチ:**
            - Validation: ドメイン部分を抽出し、自社で管理している「禁止ドメインリスト」と照合する。
            - ドメインのMXレコード（メール受信用のDNSレコード）が存在するかを確認し、一時的な使い捨てメールサービスを弾く処理を入れることもある。
    - **ケースB: とにかく登録のハードルを下げたい場合（C向けサービス）**
        - **要件:** ユーザーの入力ミスによる離脱を防ぎたい。
        - **アプローチ:**
            - Validation: 極めて緩くし（`@`が含まれているか、程度）、すぐにVerificationメールを送信する。
            - UX向上: ユーザーが `gmil.com` などと入力した場合、「もしかして gmail.com ですか？」とサジェストする機能をフロントエンドに実装する。
- ビジネス要件（セキュリティを重視するか、コンバージョン率を重視するか）によって、Validationの厳しさとVerificationのタイミングを調整する必要がある

- 正規表現を用いた書き方
```python
import re
from typing import List

class Solution:
    def numUniqueEmails(self, emails: List[str]) -> int:
        unique_emails = set()
        
        pattern = r"^([^+@]+)(?:\+[^@]*)?@(.*)$"
        
        for email in emails:
            match = re.match(pattern, email)
            if match:
                local_part = match.group(1)
                domain_part = match.group(2)

                local_part_clean = re.sub(r"\.", "", local_part)

                unique_emails.add(local_part_clean + "@" + domain_part)
                
        return len(unique_emails)
```
